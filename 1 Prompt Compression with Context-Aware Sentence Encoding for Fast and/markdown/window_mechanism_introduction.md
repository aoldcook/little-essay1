# 窗口机制（Local Context Window）说明

这份文档用于解释你当前 `context-aware encoder` 中加入的**窗口机制**，包括：

- 它是什么
- 为什么要引入
- 它在代码里如何实现
- 它解决了什么问题
- 它的优点与局限
- 在论文里可以如何表述

---

## 1. 什么是窗口机制

窗口机制指的是：

> 在为某个目标句子构造 `marked context` 时，不再使用**完整上下文**，而只保留该句子附近的一小段局部上下文。

原始思路是：

- 给定完整上下文 `C = {s_1, s_2, ..., s_n}`
- 选中第 `i` 个句子 `s_i`
- 构造：

```text
s_1 ... s_{i-1} <sent_start>s_i</sent_end> s_{i+1} ... s_n
```

也就是把**完整上下文**送进编码器。

而窗口机制改成：

- 只截取目标句前后若干句
- 构造一个**局部上下文窗口**
- 再在这个窗口里用 `<sent_start>` 和 `<sent_end>` 标记目标句

例如原文句子为：

```text
A, B, C, D, E, F, G
```

如果目标句是 `D`，那么完整上下文版可能是：

```text
A B C <sent_start>D</sent_end> E F G
```

而窗口机制可能变成：

```text
B C <sent_start>D</sent_end> E F
```

这样就只保留目标句周围的局部信息。

---

## 2. 为什么要引入窗口机制

引入窗口机制的直接原因，是为了解决长文本情况下的**输入截断问题**。

### 2.1 原始问题

当前 `context-aware encoder` 使用的是类似 `Qwen/Qwen3-Embedding-8B` 这样的编码器。  
这类模型通常有最大输入长度限制，例如：

\[
L_{max} = 512
\]

当上下文很长时，如果你仍然使用“完整上下文 + marker”的方式，那么经过 tokenizer 之后，输入可能会被截断。

一旦被截断，就会出现两种风险：

1. `<sent_start>` 在，但 `<sent_end>` 被截掉
2. 目标句本身只保留了一部分

这会导致模型在 `_find_marker_span()` 中找不到完整的 marker 区间，最终报错：

```python
ValueError: marker tokens not found in input_ids
```

---

### 2.2 更深层原因

即使不报错，完整上下文编码还有一个现实问题：

> 对每个句子都重新编码一遍完整长文本，推理成本非常高。

假设一段文本有 `n` 个句子，那么当前方法需要做：

- 对每个句子都构造一个 marked context
- 对每个 marked context 都跑一次 encoder

复杂度近似为：

\[
O(n \cdot \text{EncoderForward}(L))
\]

其中：

- `n` 是句子数
- `L` 是输入长度

如果 `L` 很大，那么整体成本会明显升高。

因此，窗口机制不仅是为了解决报错问题，也是为了：

- 降低推理开销
- 控制输入长度
- 使 context-aware encoder 更稳定地应用于长文本

---

## 3. 窗口机制在代码中的实现思路

当前窗口机制的核心函数是：

```python
build_marked_context_window(...)
```

它的大致逻辑是：

1. 一定保留目标句
2. 以目标句为中心，向左和向右逐步扩展
3. 只要加入相邻句后总长度不超过预算，就继续加入
4. 最终形成一个局部上下文窗口
5. 对目标句加上：

```text
<sent_start> ... <sent_end>
```

### 3.1 输入

- `sentences`：整段文本切好的句子列表
- `target_index`：当前目标句下标
- `marker_start`：起始标记
- `marker_end`：结束标记
- `max_chars`：窗口最大字符数预算

---

### 3.2 主要过程

首先保留目标句：

```python
selected = [target_index]
```

然后向左右两侧扩展：

- 如果左边句子还能装下，就加左边
- 如果右边句子还能装下，就加右边
- 直到预算用完

这样最终得到的是一个“以目标句为中心的局部片段”。

---

### 3.3 为什么按字符数控制，而不是按 token 数控制

当前最小实现里使用的是：

```python
max_chars=220
```

也就是按字符数近似控制窗口大小。

这样做的原因是：

1. 对中文更简单直接  
   `split()` 不适合中文，字符数通常比词数更稳

2. 不需要额外为每个候选窗口重复跑 tokenizer 统计 token 数

3. 对工程原型更轻量  
   先保证方法能跑通，比一开始追求最精确预算更重要

当然，后续如果你要做更严谨的版本，也可以改成：

- 按 tokenizer 的 token 数控制窗口预算

---

## 4. 窗口机制具体解决了什么问题

### 4.1 解决 marker 被截断的问题

这是最直接的收益。

原先完整上下文版在长文本时可能出现：

```text
<sent_start> 在输入里，但 <sent_end> 被截断掉
```

窗口机制把输入长度限制在较小范围内，因此 marker 一般都能完整保留。

---

### 4.2 降低输入长度

完整上下文版每次都把整段文本重新送入模型。  
窗口版只送局部区域，长度显著缩短。

这意味着：

- 更省显存
- 更快
- 更稳定

---

### 4.3 保留“局部上下文感知”能力

窗口机制虽然不是完整上下文，但仍然保留了：

- 前文线索
- 后文线索
- 局部篇章关系
- 句子附近的指代与过渡信息

因此它仍然比“孤立句子编码”更强。

也就是说，它是一种折中：

- 不像完整上下文那样昂贵
- 又比单句编码更有上下文信息

---

## 5. 窗口机制与普通句子编码的区别

### 5.1 普通句子编码
只编码：

```text
s_i
```

这种方法得到的是**孤立句向量**。

缺点是它看不到：

- 句子前后文
- 指代对象
- 逻辑关系
- 段落语义位置

---

### 5.2 完整上下文感知编码
编码：

```text
C with marked sentence
```

优点是上下文信息最完整。  
缺点是：

- 长文本容易截断
- 推理成本高

---

### 5.3 窗口式上下文感知编码
编码：

```text
local_window(C, s_i) with marked sentence
```

优点是：

- 保留局部上下文信息
- 避免超长截断
- 更适合长文本工程落地

因此它是一个更现实的折中方案。

---

## 6. 为什么窗口机制适合你现在的论文任务

你的论文目标不是纯粹做句子检索，而是：

> 在尽可能保留原有语义的前提下，对长文本进行压缩。

在这个目标下，窗口机制有三个优点。

### 6.1 它允许 context-aware encoder 应用于长文本

如果没有窗口机制，context-aware encoder 只能在较短文本上稳定工作。  
一旦文本变长，完整上下文就容易超过编码器上限。

窗口机制使得它可以安全用于长文压缩。

---

### 6.2 它更适合做 BGE 对比实验

你现在想做：

- `BGE + learned budget`
- `context-aware encoder + learned budget`

如果 `context-aware encoder` 因为长文本直接跑不动，那这个对比就没法做。

窗口机制让这条线真正可运行，从而能和 BGE 做公平比较。

---

### 6.3 它体现了“效率—效果折中”的方法意识

这对论文是加分项。

因为你不是简单地说：

> 完整上下文最好，所以我全都喂进去

而是明确做了一个设计选择：

> 为兼顾上下文建模能力与推理效率，我们采用局部窗口近似 sentence-in-context representation。

这比单纯堆模型更像一个成熟的方法设计。

---

## 7. 窗口机制的优点

可以概括为以下几点：

### 7.1 稳定
避免长输入导致 marker 被截断。

### 7.2 高效
减少每次编码的上下文长度，降低推理开销。

### 7.3 保留局部语义
仍然能够建模目标句前后的局部上下文依赖。

### 7.4 易于与现有框架融合
它不需要推翻现有 pipeline，只需要替换 `marked context` 的构造方式。

### 7.5 适合当前实验阶段
能帮助你先把 `BGE + learned budget vs context-aware encoder + learned budget` 这条主实验跑通。

---

## 8. 窗口机制的局限

虽然窗口机制很实用，但它不是没有代价。

### 8.1 丢失远距离上下文
如果某句的重要线索不在附近，而在很远的位置，那么局部窗口可能捕捉不到。

例如：

- 前面提到实体
- 后面才出现解释
- 中间隔了很多句

这种长距离依赖，窗口机制可能弱于完整上下文编码。

---

### 8.2 窗口大小是超参数
`max_chars` 设太小：

- 上下文信息不足

设太大：

- 又可能接近模型上限
- 推理成本升高

所以窗口大小需要实验调优。

---

### 8.3 训练—推理分布可能不一致
如果你训练时仍然使用完整上下文，而推理时改成窗口上下文，那么会存在分布不一致的问题。

更规范的做法是：

- 训练和推理都采用同一种窗口构造方式

---

## 9. 在论文中可以如何表述

你可以把窗口机制写成一种**局部上下文近似策略**。

### 可用表述 1
> 为避免长上下文超出基础编码器的最大输入长度，并降低逐句重编码带来的计算成本，我们采用局部上下文窗口机制。具体而言，对每个目标句，仅保留其左右邻近句构成的局部片段，并在该片段内使用特殊标记定位目标句，从而近似获得 sentence-in-context representation。

### 可用表述 2
> Instead of encoding the entire long context for each target sentence, we construct a local context window centered around the target sentence. This design preserves nearby contextual cues while preventing marker truncation under the input length constraint of the underlying encoder.

### 可用表述 3
> 窗口机制在完整上下文建模与工程可行性之间提供了一种折中：它牺牲部分远距离上下文信息，以换取稳定性、效率和对长文本场景的适应性。

## 10. 论文中的实验建议

如果你后面要专门验证窗口机制的价值，可以设计一个小型消融实验：

### 对比设置

1. `full-context context-aware encoder`
2. `windowed context-aware encoder`
3. `plain sentence encoder`

### 比较指标

- 相关句排序质量
- 最终 QA / 摘要指标
- 平均推理耗时
- 平均输入长度
- 是否出现 marker 截断错误

### 想验证的问题

- 窗口机制是否显著降低推理成本？
- 窗口机制是否在长文本场景下更稳定？
- 窗口机制是否比孤立句子编码更有效？

---

## 11. 一句话总结

窗口机制的本质可以概括为：

> **用目标句附近的局部上下文，近似替代完整上下文，以获得更稳定、更高效的 context-aware sentence representation。**

它不是完全等价于完整上下文编码，但在当前长文本压缩任务中，是一个非常实用且合理的工程折中方案。
